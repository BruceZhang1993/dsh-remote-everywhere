# 安全模型 — DSH Remote Everywhere

> 本文档定义威胁模型、信任边界、配对与设备授权、审批语义、以及明确的非目标。
> 协议细节见 [protocol.md](protocol.md)。

---

## 1. 安全目标

| # | 目标 | 说明 |
|---|---|---|
| G1 | **机密性** | 会话内容、文件内容、终端输出对隧道方/中继方/网络中间人不可见 |
| G2 | **完整性** | 任何帧被篡改、重排、重放都必须被检测并断开 |
| G3 | **对端认证** | 只有被明确授权的设备能连接；MITM 无法在配对时同时欺骗两端 |
| G4 | **可撤销** | 被控端能立即吊销任一设备，且吊销不可被已撤销设备绕过 |
| G5 | **审批不可绕过** | 敏感操作在被授权前不得执行；远端离线时不得静默放行 |
| G6 | **可审计** | 所有远端请求与审批决定在被控端留痕 |
| G7 | **失败闭合** | 任何鉴权/解密/协商失败都导致断开，绝不降级 |

## 2. 非目标

- **不防被控端本机已被攻陷**：如果攻击者已能在被控端以用户权限执行任意代码，他可以直接读
  会话数据，无需经过本插件。
- **不防恶意客户端滥用已被授予的能力**：配对时授予的能力范围内，客户端可以读取会话内容。
  这靠"配对需人工确认 + 逐设备吊销 + 能力位图"控制，而非靠加密。
- **不隐藏元数据**：隧道方能看到连接时间、流量大小、持续时间。Noise 只隐藏内容。
- **不做硬件级密钥保护**：移动端用 Keychain/Keystore；桌面端密钥以文件形式存储并受文件权限
  保护。不假设存在 TPM/安全隔区。
- **不防护侧信道**：流量分析、时序分析不在范围内。

## 3. 信任边界

```
┌─────────────── 被控端信任域（用户设备）───────────────┐
│  长期私钥 s_R │ 会话数据 │ 审批能力 │ 文件系统        │
└───────────────────────┬───────────────────────────────┘
                        │ ← Noise 端到端加密边界（真正的安全边界）
┌───────────────────────┴───────────────────────────────┐
│  隧道 / 中继 / 网络（**不受信任**，仅见密文）           │
└───────────────────────┬───────────────────────────────┘
                        │
┌───────────────────────┴───────────────────────────────┐
│  控制端信任域（用户设备/手机）                         │
│  长期私钥 s_I │ 已解密的会话视图                        │
└───────────────────────────────────────────────────────┘
```

**关键论断**：外层 TLS 只提供传输卫生（隐藏元数据、穿过中间盒）。它**不是**信任边界。因此：

- Cloudflare、自建中继、局域网上的任何人，都只能看到密文与流量特征。
- 即使 `trycloudflare.com` 域名泄露，攻击者拿到的也只是 Noise 加密流。
- 中继被完全攻陷也不会导致明文泄露。

## 4. 威胁与对策

| # | 威胁 | 对策 | 残余风险 |
|---|---|---|---|
| T1 | 隧道域名被扫描/泄露，攻击者尝试连接 | Noise_XX 要求认证静态密钥；未配对设备在握手阶段即失败；握手前 IP 限速 | 存在被动流量分析 |
| T2 | 配对时 MITM（攻击者截获二维码） | **必须人工比对 6 位 SAS**；prologue 绑定 `sid` 使跨会话重放失败；一次性短时效 | 用户忽略比对而直接确认 |
| T3 | 二维码被拍照后在原会话内抢先配对 | `sid` 一次性、TTL 120–300s；同一 `sid` 只允许一次成功握手；配对期间已有连接时拒绝并发 | 攻击者与用户几乎同时扫码（窗口极小） |
| T4 | 帧重放/重排 | 每流单调 `seq`；序号进入 AEAD associated data；重复或回退立即断开 | 无 |
| T5 | 密文篡改 | ChaCha20-Poly1305 AEAD；握手后每条消息认证 | 无 |
| T6 | 协议降级 | 版本与能力取交集，交集为空即断开；**不提供**任何"无加密"或"弱加密"回退 | 无 |
| T7 | 已吊销设备继续连接 | 设备表在鉴权**之前**检查；吊销立即生效并主动断开该设备现有连接 | 无 |
| T8 | 审批被静默放行 | 无客户端在线时落回本机审批；远端不可达不产生 `allowed-once`；宿主 `'never'` 策略优先且插件无法旁路 | 无 |
| T9 | 恶意客户端执行危险终端命令 | `terminal.exec` 强制先有 `allowed-once` 审批记录，且逐次审批（不缓存授权） | 用户连续批准 |
| T10 | 路径穿越读取任意文件 | 文件操作受宿主 workspace 边界约束；路径规范化后校验前缀；拒绝符号链接逃逸 | 宿主沙箱策略配置过宽 |
| T11 | 暴力破解配对 | 握手前 IP 限速（如 10 次/分钟）；配对尝试计数；失败指数退避 | 无 |
| T12 | 资源耗尽（连接洪泛） | 单设备并发连接上限；连接数上限；超限返回 `busy` | 无 |
| **T12b** | **隧道级 200 in-flight 上限被触顶** —— 实测 WebSocket 连接同样计入该额度，第 201 条返回 `HTTP/1.1 429`，且**重试无法解决**（需已有流关闭） | 客户端主动限制并发流数（默认上限 32，远低于 200）；服务端对超限返回 `busy` 而非让隧道返回 429；UI 必须把 429 与 530 区分显示 | 单设备被洪水攻击时可占满额度 → 由单设备并发上限缓解 |
| **T12c** | **新建隧道的冷启动窗口** —— 实测新建后前约 50 秒内 WebSocket 冷升级失败率 10–25%，而"URL 已打印 + HTTP 200"并不代表就绪 | 就绪探测（raw TLS RFC6455 握手 + 重试）通过后才把 URL 作为可配对状态展示；配对流程容忍退避重试 | 用户过早扫码可能失败一次，需给出明确重试提示 |
| T13 | 供应链攻击（密码学库） | 优先纯 JS / 有 prebuilt 的成熟库；锁定版本；M4 前做依赖审查 | 上游库被投毒 |
| T14 | 自实现密码学缺陷 | 用成熟原语而非自创算法；M0 建测试向量；负向测试（篡改/重放/prologue 不匹配）；M4 第三方审查 | 实现级漏洞 |
| T15 | `name` 字段冒充设备 | `name` 仅展示；鉴权与 SAS 只依赖公钥；UI 必须同时展示设备指纹 | 用户被相似的 name 误导 |
| **T16** | **X25519 低阶点攻击** —— 攻击者发送低阶 u 坐标，迫使共享密钥为全零，从而在**不知道任何私钥**的情况下使双方计算出相同的"密钥" | ✅ **已实现**：Noise 的唯一 DH 入口做全零检查并中止握手；两侧 7 个标准低阶点 + 线路层伪造临时公钥测试均通过（见 §4.1） | 无。**注意两侧不对称**：Node 的 `@noble/curves` 本就会拒绝，Dart 的 `cryptography` 完全不拒绝 → 负向测试必须两侧都跑 |
| **T17** | **密码学库的静默错误行为** —— `cryptography` 2.9.0 的 `Hmac.blake2s()` 并非 RFC 2104 HMAC，会产出**错误但在自测中自洽**的 tag，导致与第三方实现对不上而难以定位 | ✅ **已实现**：自实现 HMAC-BLAKE2s（已对 OpenSSL 在 key 长度 6/32/100 下逐字节验证）；库的错误值写成**表征测试**，依赖升级导致行为变化时立即变红（见 §4.2） | 无 |
| **T18** | **移动端被当作被控端** —— 手机丢失或被入侵即等于把桌面会话交出去 | 产品决策：**手机只做控制端**。协议要求 `role` 在 `hello` 中声明，被控端**强制拒绝**非法角色；移动端私钥仅存 Keychain/Keystore（见 §5.4） | 无 |

### 4.1 X25519 低阶点守卫（**已实现并验证**）

**M0 实测（`spikes/flutter-android/verify-crypto/REPORT.md`）**：`cryptography` 2.9.0 的
`DartX25519` **不做任何低阶点检查**。7 个标准低阶 u 坐标
（`u=0`、`u=1`、两个 8 阶点 `e0eb7a7c…` / `5f9c95bc…`、`p-1`、`p`、`p+1`）
**全部静默返回 32 个零字节**，不抛任何异常（对照：pyca/cryptography 的 Python 实现对全部 7 个
都抛 `ValueError`）。这些坐标确实都是低阶点，已用独立的 RFC 7748 爬梯实现复核。

后果：Noise 的 `e`/`ee`/`s`/`es`/`se` 每一步都做 DH。若攻击者把手里的临时公钥或静态公钥换成
低阶点，双方会得到全零的共享密钥 —— 攻击者无需知道任何私钥即可预测密钥流。这是一条**真实的
攻击路径**，且它不会让本端自测失败（两端自己是一致的），只会让安全性消失。

**实现要点（已验证）**：

- 守卫放在 Noise 的**唯一 DH 入口**：Node 为 `NoiseXX._dh`
  （`spikes/noise-interop/node/src/noise-xx.js`），Dart 为 `dh()`
  （`spikes/noise-interop/dart/lib/noise_xx_blake2s.dart`）。Noise 握手共有 6 个 DH 调用点，
  统一入口保证不会漏。
- **不要**把守卫下沉到最底层的密钥生成函数：`publicKeyFromSecret` 用基点 `u=9` 做
  `X25519(sk, 9)`。已实测该乘积**不会**为全零，因此基点路径不受影响；但保持两条路径分离，
  可以避免把"密钥生成"与"握手 DH"的行为耦合在一起。

**验证结果（`spikes/noise-interop/scripts/run-all.sh` 全绿）**：

| 测试 | 结果 |
|---|---|
| Node 自测：7 个低阶点 + 线路层伪造临时公钥 | ✅ 全过 |
| Dart 自测：JIT 与 AOT 各 31 项，含 7 个低阶点 + 线路层攻击 | ✅ 全过 |
| 基点路径未受影响 | ✅ 两侧均验证 |
| 原有验证未被破坏（向量 94 项、oracle 对照、真实 TCP 互操作 3/3） | ✅ 全过 |
| 低阶点被拒的**错误类型** | Dart `StateError`；Node `invalid private or public key received` |

**⚠️ 一个必须记录的两侧不对称（对等性风险）**：

- **Node 侧 `@noble/curves` 本来就会拒绝低阶点**（抛 `invalid private or public key received`），
  我们新增的守卫实际不会被执行 —— 但仍保留，作为对未来库版本退化以及其他实现路径的防御。
- **Dart 侧 `cryptography` 完全不拒绝**，守卫是唯一防线。

含义：这条负向测试**必须在两侧都跑**。若只在一侧实现，另一侧可能因为换库而静默失去防护。
两侧的错误来源与措辞都不同，因此跨语言一致性测试应当断言**"握手被中止"**这一行为，
而不是断言具体错误消息。

```dart
// 概念示意：统一入口，任何 DH 调用点都不得绕过
Uint8List dhChecked(SimpleKeyPair sk, SimplePublicKey pk) {
  final shared = x25519.sharedSecretSync(sk, pk);
  if (shared.every((b) => b == 0)) {
    throw NoiseHandshakeError('X25519 low-order point rejected (all-zero shared secret)');
  }
  return shared;
}
```

### 4.2 把库的错误行为固化为表征测试

`cryptography` 2.9.0 的 `Blake2s.blockLengthInBytes` 返回 32（真实值 64），
`Blake2b` 返回 64（真实值 128）—— 错误恰好都减半，且**被包自身的测试固化**，短期内不会修。
任何基于它的 `Hmac(...)` / `Hkdf(...)` 都会产出错误结果。危险之处在于**自测自洽**：
两端都用同一个错误实现时握手能成功，只有与第三方实现或规范向量对照才会暴露。

因此要求：

1. **绝不调用** `Hmac.blake2s()` 或 `Hkdf(hmac: Hmac.blake2s())`。
2. 自实现 HMAC-BLAKE2s（RFC 2104，`B = 64`），并**对 OpenSSL 逐字节验证**。
3. 把库的错误输出写成**表征测试**（记录 `Hmac.blake2s("secret","abc")` = `773a1d7d…`、
   `Hkdf(...)` = `7077bc75…` 这些**已知错误值**）。将来依赖升级若改变了这些值，测试立即变红，
   迫使维护者重新评估，而不是静默改变线上互操作行为。

验证证据：HMAC-BLAKE2s（B=64）对 OpenSSL 在 key 长度 6 / 32 / 100 字节（含 >64 字节需先哈希的
分支）下全部逐字节一致；`Hkdf(Hmac.blake2s())` 的错误输出已在 Python 中精确复现根因。

## 5. 配对设计

### 5.1 为什么是"二维码 + SAS"而不是"二维码里放 token"

二维码可以被拍照、被截屏、被远程看到。如果二维码本身就是凭据（bearer token），那么**任何
看到它的人都能配对**。

KDE Connect 的 **CVE-2020-26164** 是这一设计最直接的反面教材：其配对流程长期只显示
**攻击者完全可控的设备名**，安全审计后的修补是**显示双方证书公钥拼接后的 SHA-256 指纹**，
让人类可以验证。

因此本项目的配对要求：

1. 二维码只携带**会话参数**（`sid`、`exp`、`relay`、被控端静态公钥、展示名、能力），
   **不含任何长期凭据**。
2. 握手 transcript 绑定 `sid`（prologue），使二维码跨会话重放无效。
3. 两端显示**由握手结果推导**的 6 位 SAS，用户人工比对。
4. SAS 比对是**强制的**，首次配对不提供"跳过"。
5. 配对成功后才把对方长期公钥写入设备表。

### 5.2 设备标识与指纹

```
deviceId = base64url( SHA256( 长期 X25519 静态公钥 ) [0..16] )
```

UI 必须同时展示 `name` 与 `deviceId` 前缀，让用户可以识别"名字对但指纹不对"的冒充。

### 5.3 能力位图

配对时被控端明确授予能力集合，作为该设备的授权上限：

| 能力 | 覆盖的方法 |
|---|---|
| `session` | `session.*`、`stream.*`、`history.*` |
| `approval` | `approval.*`、`question.*` |
| `files` | `files.*` |
| `terminal` | `terminal.exec` |
| `admin` | `device.*`、`pair.*` |

能力是**授权上限**而非自动通过：`terminal` 能力只表示"允许发起终端请求"，每次执行仍需审批。

### 5.4 角色限制：手机只做控制端（T18）

**产品决策（2026-10-10）**：移动端 App **只做控制端**，被控端仅限 DSH 实例。

理由：手机丢失或被入侵的风险特征与桌面机完全不同。若手机可被控，则一部失窃手机等于把桌面
会话、文件系统与终端交到攻击者手里；而"手机作为控制端"的最坏后果是攻击者能操作自己的手机去
连自己的机器，风险面小得多。这条限制是**安全边界**，不是便利性取舍。

协议层面的强制要求：

| 要求 | 说明 |
|---|---|
| `hello` 必须声明 `role: "controller" \| "controlled"` | 见 [protocol.md](protocol.md) §4 |
| 被控端默认**只接受** `role: "controller"` 的对端 | 未声明或声明为 controlled 的对端，在 `hello` 阶段即被拒绝（`unauthorized`） |
| DSH 实例间的控制端/被控端互连不受此限制 | `role` 由部署配置决定，不是硬编码；本条只约束"移动端不得作为被控端" |
| 违反角色限制必须**审计留痕** | 记录 `deviceId`、对端声明的角色、时间与拒绝原因 |

实现注意：这条检查必须放在鉴权之后、任何能力方法之前，且**不能只依赖客户端自报的
`role`** —— 真正的边界是"移动端分发渠道不提供被控端能力"，服务端的 `role` 检查是纵深防御的
第二层，用于拒绝被篡改的客户端。

## 6. 设备授权与吊销

- 被控端维护设备表：`{deviceId, name, caps, pairedAt, lastSeenAt, revokedAt?}`。
- **吊销必须立即生效**：从设备表移除后，任何使用该公钥的握手失败；已有的活跃连接被主动断开。
- 吊销是**单向且不可被被吊销方绕过**的：被吊销设备无法通过重新握手恢复，必须重新走完整配对
  流程（需要本机物理/UI 确认）。
- 设备表持久化在被控端；插件重启后仍然有效。

## 7. 审批模型（双向、竞速、不静默放行）

需求原文：**"控制端和被控端都支持审批，完整对标 codex remote access"**。

### 7.1 语义

```
DSH 工具即将执行敏感操作
        │
        ▼
宿主 ctx.on('approval/request') 瀑布
        │
        ├─ 策略为 'never' ──► 直接 'rejected'（插件无权干预）
        │
        └─ 策略为 'ask'
              │
              ├─ 被控端本机 UI 呈现（原有行为，始终保留）
              └─ 若有已授权且在线、且具备 approval 能力的客户端
                    └─ 推送 approval.request，等待 approval.decide
                         │
                         ▼
              第一个返回的决定胜出（本机或远端）
              超时 → 'cancelled'（不是 'allowed-once'）
```

### 7.2 硬性规则

| 规则 | 理由 |
|---|---|
| 远端离线或无权时，**落回本机审批** | 保证可用性，且不产生远端隐式授权 |
| 远端不可达**绝不**产生 `allowed-once` | 失败闭合 |
| 超时产生 `cancelled` 而非允许 | 失败闭合 |
| 每次请求独立审批，**不缓存授权** | 审批是 one-shot 语义 |
| 宿主的 `'never'` 策略**优先且不可旁路** | 保留用户显式的严格姿态 |
| 决定写入宿主审计（`approval/asked` / `approval/decided`） | 可审计性 |
| 时间限制：`terminal.exec` 每次审批 | 降低单次误批的影响面 |

### 7.3 并发与竞速的取舍

本机 UI 与远端客户端**竞速，先到先得**。这带来一个接受的风险：用户在手机上快速点了"允许"，
而本机上本来会看到更详细的信息。缓解措施：

- 两端展示**同样的**请求上下文（工具名、调用参数、理由）。
- 可通过配置改为"仅本机"或"仅远端优先"（策略旋钮，默认竞速）。
- 所有决定都带 `by: 'local' | 'remote'` 记录，事后可查。

## 8. 密钥与存储

| 项 | 存储位置 | 保护 |
|---|---|---|
| 被控端长期私钥 `s_R` | profile 目录下，文件权限 0600 | 文件系统权限 |
| 控制端（DSH）长期私钥 `s_I` | 同上，各自 profile | 文件系统权限 |
| 移动端长期私钥 | Android Keystore / iOS Keychain | 平台密钥库 |
| 设备表 | 被控端 profile 持久化 | 文件权限 |
| 会话密钥 | 仅内存，进程退出即销毁 | — |
| 配对临时 `sid` | 仅内存，一次性 | TTL |

**明确不存储**：明文会话内容不因本插件而落盘（除宿主自身已有的会话持久化）。
移动端本地缓存的会话视图需加密（M3 决定具体方案：加密 JSON 文件 vs 数据库加密）。

## 9. 审计

被控端记录（不含明文载入内存之外的内容）：

- 连接事件：`deviceId`、时间、来源 IP、结果（成功/失败/失败原因）
- 方法调用：方法名、`deviceId`、时间、结果状态（**默认不记参数内容**，避免审计日志本身成为
  敏感数据泄露源；可按需开启详细模式）
- 审批：`approvalId`、工具名、决定、决定方（local/remote）、时间
- 吊销与配对事件

审计记录与宿主会话审计（`approval/asked`/`approval/decided`）互相独立但**时间线可对齐**。
